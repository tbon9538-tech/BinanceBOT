- 研究集为 2020-01-01～2025-06-30；补充检验区间为 2018-06-01～2019-12-31。
- 基线是 spec v3 的默认配置。
- 每个实验通过之后，以**通过的配置**作为下一个实验的基线；没有通过时，保持原基线不变。
- 每个实验开始前，先在 `doc/research/log.md` 写下假设、经济学理由、取值网格和通过标准（即"预注册"），然后才能运行。

| 11 | E8 | 调仓时点：tranches、单一调仓日；**容忍带模式**：absolute（0.02）vs relative（`threshold_rel` ∈ {0.15, 0.25, 0.40}） | 7 + 3 + 4 | 不同调仓日之间的离散程度；Sharpe、成本、跟踪误差（相对于不设容忍带）；**卫星袖子的实际调仓频率**（每月交易笔数、平均每笔金额、跳过原因分布） | 平滑模式下的离散程度明显更小；容忍带模式与 `threshold_rel` 的默认值由本实验决定：在成本相当时选跟踪误差更小的，差异在噪声内时选 relative 0.25 |
| 12 | E9 | 成本压力；**按真实资金量回测**：`initial_capital` ∈ {500, 2000} USDT，严格应用最小下单额、`min_trade_usdt` 和容忍带 | 3 + 分档滑点 + 2×2（两种资金量 × 真实/理想） | 夏普 / Calmar 的下降幅度；真实与理想情况的收益差和跟踪误差；实际调仓频率 | 成本 ×2 时仍满足 spec §1.1 的硬约束；500 USDT 下与理想情况的年化收益差 < 2 个百分点，否则在报告中给出建议的最低资金量 |
| 13 | E10 | DSR、walk-forward、block bootstrap（PBO/CSCV 放后续版本） | — | DSR（试验数 = trials.csv 的总行数）、walk-forward 拼接曲线、bootstrap 下的 MDD 分布 | DSR > 0.9 为"强"，0.5～0.9 为"弱"，< 0.5 时须在提案中说明 |
| 14 | E11 | 保留集（C1 之后） | 1 | 全部指标 | 见 research §4 的退化路径 |

## 4. 防过拟合规则（强制执行）

1. **每个参数都必须有经济学解释**，在运行之前写进研究日志。"回测出来最好"不能作为唯一理由。
2. **看邻域，不看单点**：选的是一片高原，不是一个尖峰。邻域内主指标的均值必须 ≥ 选定值的 80%，否则视为不稳健，退回默认值或更简单的方案。
3. **一次只改一个变量**。每个实验结束后，结论记入 `doc/research/log.md`。格式如下：

   ```
   ## E3b momentum_skip（2026-xx-xx，commit abc123）
   假设：……  经济学理由：……  网格：{0,1,3,5}  通过标准：research §0.3
   结果：（表格，或报告路径）
   结论：通过 / 未通过；采用值：0；理由：……
   试验数累计：37
   ```

4. **保留集纪律**：
   - 2025-07-01 及之后的数据是最终保留集。研究期间，代码层面强制禁止读取（spec §3.6）。
   - 参数确定后（检查点 C1），只运行一次 `holdout --final`。
   - 保留集运行之后**不得再改参数**。结果不达标时，可以接受结果、退化方案，或者回到研究阶段并重新设计；如果重新设计，新方案的检验改用 demo 前向运行的数据，保留集不能再作为检验。
5. **结果异常时先排查 bug**：Sharpe > 3、权益曲线异常平滑（例如月度胜率 > 90%）、或者某个改动让 Sharpe 提高超过 0.5 时，先停下来排查以下几项，再解读结果：
   - **前视偏差**：信号是否用到了 t+1 的数据；滚动窗口是否包含当天的成交价；标的池是否用到了未来的成交额或存活信息；收益是否和权重在同一天对齐。
   - **幸存者偏差**：已下架的币是否真的在数据里；交易段切分是否把下架前的暴跌切掉了。
   - **成本**：成本是否按双边、按实际换手扣除；最小下单额和取整是否生效。
   - **数据**：微秒时间戳是否被当成毫秒；有没有重复的日线；同名复用是否没有切段。
   - 排查记录写进研究日志。
6. **试验计数**：每次运行的配置都追加到 `doc/research/trials.csv`，包括失败的和被放弃的。DSR 按总试验数计算。
7. **报告全部结果**：实验报告要列出整个网格的结果，不能只挑最好的。
8. **简单优先**：两个方案的差异在噪声内（Sharpe 差 < 0.2，且两段方向不一致）时，选参数更少、规则更简单的那一个。
9. **不受保留集行情的先验影响**：做参数决定时，只依据研究集数据和事先写好的理由。研究人员（包括 Claude）对 2025-07 之后行情的任何印象（例如某段时间 BTC 或山寨币涨跌如何），都不能作为选参或改规则的理由；如果研究日志里的理由引用了这类印象，该决定作废重来。

## 5. 风险点：最容易出 bug 的地方（按严重程度排序）

| # | 风险点 | 后果 | 预防措施 |
|---|---|---|---|
| 1 | 执行状态未知时重复下单（spec §6.6） | 仓位翻倍 | write-ahead 意图日志；没有"换 ID 重下"的代码路径；mock 测试覆盖全部分支；故障演练 |
| 2 | Decimal 取整与过滤器（spec §6.3） | 订单被拒，或超出价格保护 | 全程使用 Decimal；属性测试；用 testnet 上真实的过滤器做回归 |
| 3 | 回测前视（spec §9.6） | 研究结论无效 | 人造数据测试；执行回放做交叉校验；按 §4 第 5 条排查 |
| 4 | 时间戳单位（微秒和毫秒混用）、没有表头的 CSV | 日期整体错位 | 夹具测试；加载后检查日期是否连续 |
| 5 | 持仓数量与手续费扣除（spec §6.5 第 4 条、§6.9） | 卖出时余额不足、对账差异 | 以交易所余额为准；卖出数量按 free 余额计算 |
| 6 | 平滑与止损剔除的逻辑（spec §4.4） | 按旧信号买回、Risk-Off 时没有清零 | 针对每条规则单独写测试 |
| 7 | 签名前没有 percent-encode | 全部私有请求返回 -1022 | 用官方示例作为测试向量 |
| 8 | 时钟偏移和 recvWindow | 请求被拒 | 每次运行先同步时钟 |
| 9 | testnet 每月重置 | 对账报告大量差异 | 识别出"余额全部重置"的模式后，给出明确告警与恢复指引（演练第 5 项） |
| 10 | Windows 与 Linux 的差异（路径、换行、时区、文件锁） | 部署后才暴露问题 | 统一使用 UTC 和 pathlib；在 CI 或本地同时跑 Windows 和 Linux（WSL 或 Docker） |
| 11 | 代币化股票等新资产混入标的池 | 交易到非加密资产 | 白名单机制；新资产默认不交易 |
| 12 | 限频与 IP 封禁 | 整天无法运行 | 读取响应头；429/418 时全局退避；日频策略的请求量很小，只要不写循环重试就不会触发 |

## 6. 测试策略

### 6.1 单元测试（pytest，不访问网络）

- 覆盖 spec §14 第 1 条的全部内容。HTTP 一律用 `httpx.MockTransport` 模拟，禁止访问真实网络。CI 中设置 `pytest --disable-socket` 或等价手段。
- 过滤器与取整使用 `hypothesis` 做属性测试。
- 核心模块的覆盖率目标：`strategy/`、`execution/`、`risk/` 的行覆盖率 ≥ 90%。

### 6.2 回测正确性测试

1. **无前视**：在人造数据的 t+1 日放入一个极端值（例如价格 ×100），t 日及之前的目标和 NAV 必须完全不受影响。
2. **已知答案**：
   - 单币恒定日收益 r、无成本、权重恒为 w 时，NAV 应为 `(1 + w × r)^n`；
   - 两个币每 30 天交替领涨时，换仓日期与人工计算一致。
3. **成本守恒**：`Σ 成本 = Σ |成交额| × 单边成本率`。
4. **下架**：持仓币的数据中断时，按 haircut 退出，NAV 的跳变与计算一致。
5. **交易段**：在同名复用数据上，新段的前 90 天不能进入标的池。
6. **一致性**：研究引擎与执行回放的 NAV 差异 < 1%（M6-6）。
7. **保留集守卫**：见 M1-5。

### 6.3 集成测试（使用 SimSpotAccount）

- 完整运行 `run_once` 的场景：首次建仓、日常调仓、Risk-Off 清仓、资金不足时按比例缩小、灰尘、持仓币状态变为 BREAK、`KILL` 文件。
- 可以注入故障的 SimSpotAccount：可配置下单超时、5xx、部分成交、-2013、余额被外部修改。

### 6.4 testnet 联调清单（M5-9）

1. 确认 Key 类型并做签名自检（`python -m bot status` 能返回余额）；
2. `run --once --dry-run`：订单计划合理；
3. `run --once --force-rebalance`：执行并对账；
4. 立即再运行一次 `run --once`：零订单；
5. 人为修改目标后再运行：只交易差额；
6. 记录每笔订单的 clientOrderId、状态和成交，与数据库核对。

### 6.5 故障演练（M6-7）

1. 在卖单之后、买单之前杀掉进程 → 重启后只补买单；
2. 注入超时（SimSpotAccount 和 testnet 各演练一次；testnet 可以用极短的超时模拟）→ 走 §6.6 的流程，不会重复下单；
3. `KILL` 文件 → 撤单、清仓、进入 KILLED 状态，重启后不会自动交易；
4. 断网后运行 → 失败、告警；恢复网络后下一次运行正常；
5. 模拟 testnet 余额重置 → 对账发出告警，`UNEXPLAINED_BALANCE_CHANGE` 禁止买入，人工确认后恢复。

### 6.6 demo 前向运行（M7-3）

- 每日：对账无差错，日报完整。
- 每周：比较实际成交价与 t+1 开盘价（回测假设）之间的偏差，以及实际手续费；把同期的 demo NAV 与研究引擎的模拟结果对比。
